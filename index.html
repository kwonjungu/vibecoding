STEP 01

더 나은 바이브코딩을 위한 배경지식

이 칸에는 실습이 없습니다. 대신 시작하기 전에 판단해야 할 것 네 가지를 정리합니다. 무엇을 만들지 정하는 법과 도구를 고르는 기준, 그리고 고칠 때의 순서와 지켜야 할 선입니다. 이 네 가지를 먼저 잡아 두면 다음 칸부터 훨씬 덜 헤맵니다.

시작 전에 잡아 둘 네 가지

설계 목적 설정

무엇을 만들까에서 출발하면 끝이 없습니다. 무엇이 불편한가에서 출발합니다. 만들기 전에 한 줄로 적습니다. 누가, 어디서, 무엇을, 몇 분 안에 하는지입니다. 예를 들면 이렇습니다. 4학년 25명이 전자칠판 앞에서 지도 퀴즈를 10분 안에 푼다. 이 한 줄이 프롬프트의 뼈대가 되고 동시에 이 정도면 됐다고 말할 기준선이 됩니다.

누가 · 어디서

4학년 25명이 전자칠판 앞에서 씁니다. 사람 수와 장소가 정해지면 화면 크기와 글자 크기가 따라 정해집니다.

무엇을

지도 퀴즈 하나입니다. 기능을 하나로 좁힙니다. 기능이 둘이 되는 순간 완성까지의 거리가 네 배가 됩니다.

몇 분 안에

10분입니다. 시간을 적어 두면 여기서 멈춰도 된다는 선이 생깁니다. 이 선이 없으면 계속 고치게 됩니다.

도구 선택

도구마다 열어 주는 문이 다릅니다. 식당에 빗대면 🟡 홀만 손보는 도구가 있고 🟦 주방 열쇠까지 주는 도구가 있습니다. 이번 연수는 설치가 필요 없는 두 가지만 씁니다.

Canvas

제미나이 안에서 화면을 만들고 바꾸는 인테리어 앱입니다. 앱 파일 한 개를 빠르게 뽑을 때 좋습니다.

AI Studio

주방 열쇠에 해당하는 AI 사용 열쇠(API 키)까지 주는 작업실입니다. 여러 파일로 된 앱을 다룹니다.

설치형 도구

설계와 시공과 입주를 한꺼번에 맡기는 공사업체입니다. 학교 컴퓨터에 설치 권한이 없어 이번에는 빼 둡니다.

고르는 기준은 셋입니다. 학교 컴퓨터에 설치할 수 있는지, 무료로 쓰는 조건이 무엇인지, 한도가 잠기면 수업이 멈추는지를 봅니다.

과정

한 번에 완성되지 않습니다. 대화로 다가갑니다. 처음에는 크게 한 번 만들고 그다음부터는 한 번에 하나씩만 고칩니다. 두 가지를 같이 고치면 어느 쪽이 화면을 망가뜨렸는지 알 수 없게 됩니다.

크게 한 번

처음 프롬프트에는 무엇을 만들지와 어떻게 보일지 그리고 누구를 위한 것인지를 함께 적습니다.

백업 먼저

고치기 전에 파일을 복사해 index_백업.html로 남깁니다. 가장 값싼 안전장치입니다.

하나씩만

색을 바꿨으면 화면을 확인하고 그다음에 글자 크기를 바꿉니다. 순서를 지키면 되돌리기가 쉽습니다.

마인드셋

오류는 실패가 아니라 정보입니다. 빨간 글씨가 나오면 그대로 복사해 AI에게 붙여넣는 것이 가장 빠릅니다. 안 돼요라고 말하는 대신 어디까지 됐고 무엇을 눌렀을 때 무엇이 나왔는지를 말합니다. 세 번 시도해도 안 되면 백업 파일로 돌아갑니다. 지켜야 할 선도 분명합니다. 학생 이름과 얼굴은 공개 저장소에 올리지 않고 API 키는 코드에 넣지 않습니다.

오류 다루기

화면에 뜬 문구를 한 글자도 바꾸지 말고 복사해 붙여넣습니다. 요약해서 옮기면 AI도 짐작만 합니다.

학생 정보

학생은 회원가입 없이 학급 코드와 번호로 들어옵니다. 학급 코드는 수업이 끝나면 바꿉니다.

열쇠와 자료

API 키는 서버에만 둡니다. 교과서 지문이나 삽화가 들어간 앱은 교실 안에서만 씁니다.

시작하기 전 확인

  • 만들기 전에 누가 어디서 무엇을 몇 분 안에 하는지 한 줄로 적었습니다.
  • 고치기 전에 백업 파일을 만들어 두었습니다.
  • 지금 한 번에 하나만 고치고 있습니다.
  • 화면과 파일 어디에도 학생 이름이나 얼굴이 들어가지 않았습니다.
  • API 키가 코드 안에 적혀 있지 않습니다.

STEP 02

웹페이지 디자인 — 같은 내용, 다른 인상

이 칸의 주제는 만들기가 아니라 디자인 바꾸기입니다. 이미 있는 활동지를 그대로 두고 보이는 것만 바꿉니다. 문항도 정답도 손대지 않습니다.

왜 필요한가

바이브코딩으로 만든 활동지는 누가 만들어도 비슷하게 생깁니다. 보라색 그라데이션 배경 위에 둥근 카드가 떠 있고, 제목마다 이모지가 붙고, 글자는 전부 가운데로 모입니다. 솜씨의 차이가 아닙니다. 아무도 디자인을 지시하지 않아 AI의 기본값이 그대로 나온 것입니다.

DESIGN.md를 건네면 그 기본값이 바뀝니다. DESIGN.md는 색과 글꼴, 간격과 화면 조각 규칙을 마크다운 한 장에 적어 AI에게 넘기는 디자인 명세서입니다. 식당으로 치면 홀의 인테리어 도면입니다. 도면을 주지 않으면 시공하는 쪽은 늘 하던 대로 꾸밉니다.

이렇게 합니다

  1. Gemini Canvas에 활동지 프롬프트를 넣어 앱 파일 한 개(index.html)를 만듭니다. 메모장에 저장할 때 세 가지를 확인합니다. 파일 형식은 모든 파일, 이름은 index.html, 인코딩은 UTF-8입니다. 저장한 파일을 더블클릭하면 브라우저에서 열립니다.

  2. 저장소의 demo/worksheet-before.html을 엽니다. 4학년 사회 "우리 지역의 문화유산" 활동지이고, 일부러 전형적으로 만든 표본입니다. 앞 단계에서 못 만들었거나 실패했다면 이 파일로 3단계부터 바로 이어갑니다. 디자인 실습이 만들기에서 막히면 안 되기 때문입니다.

    표본 활동지 열기

  3. 왜 다 비슷한지 눈으로 확인합니다. 보라색 그라데이션 배경, 20px 라운드 카드, 짙은 그림자, 제목마다 붙은 이모지, 전부 가운데 정렬, 그리고 맨 아래의 "Made with ♥ by AI" 한 줄입니다. 여섯 가지가 거의 항상 같이 나옵니다.

  4. DESIGN.md가 무엇인지 확인합니다. 파일 하나를 프로젝트에 넣어 두고 AI에게 함께 건네면, AI가 그 규칙대로 화면을 만듭니다. 색을 하나하나 지시하지 않아도 됩니다.

  5. getdesign.md에서 쓸 명세를 고릅니다. 브랜드 명세 70여 종을 미리보기하고 그대로 복사할 수 있습니다. 수업용으로는 대비가 뚜렷한 것을 권합니다. 글자가 작고 회색이 많은 명세는 전자칠판에서 잘 안 보입니다.

    getdesign.md 열기

  6. AI Studio나 Canvas에 활동지 HTML 전체와 DESIGN.md 전문을 함께 넣고 다시 만들어 달라고 합니다. 아래 프롬프트를 그대로 붙여 넣으면 됩니다.

  7. 두 파일을 탭 두 개에 나란히 띄워 비교합니다. 바뀐 것은 색과 여백, 글꼴과 정렬입니다. 문항과 정답은 하나도 바뀌지 않았습니다. 이것이 이 칸에서 확인할 전부입니다.

복붙 프롬프트

아래 DESIGN.md에 맞춰 이 활동지를 다시 만들어 주세요.
문항과 정답은 하나도 바꾸지 말고 보이는 것만 바꿔 주세요.
완성된 index.html 전체를 생략 없이 코드블록 하나로 주세요.

[여기에 getdesign.md에서 복사한 DESIGN.md 전문을 붙여 넣습니다]

[여기에 활동지 HTML 전체를 붙여 넣습니다]

이러면 성공입니다

  • 두 파일의 문항이 같습니다. 1번부터 4번까지 문장이 그대로입니다.
  • 보라색 그라데이션이 사라졌습니다. 배경이 한 가지 색으로 차분해졌습니다.
  • 제목에 이모지가 없는데도 무엇을 하는 화면인지 읽힙니다.

막히면

문항까지 바뀌어 버렸습니다

증상. 디자인은 바뀌었는데 문제 번호나 보기 문장이 다른 말로 고쳐져 있습니다.

원인. 내용을 바꾸지 말라는 문장을 프롬프트에서 빼먹었습니다. 그러면 AI는 더 좋게 다듬는 일까지 자기 몫으로 봅니다.

해결. 위 프롬프트의 둘째 줄을 넣고 다시 요청합니다. 이미 망가졌다면 원본 파일을 다시 붙여 넣고 처음부터 시킵니다.

코드가 중간에 잘렸습니다

증상. 받은 코드 끝이 잘려 있거나 중간에 생략을 뜻하는 표시가 들어가 있습니다.

원인. 생략 없이 전체를 달라고 하지 않았습니다. 요청이 없으면 AI는 바뀐 부분만 보여 줍니다.

해결. "index.html 전체를 생략 없이 코드블록 하나로 주세요"라고 다시 말합니다. 그래도 잘리면 "이어서 끝까지 주세요"라고 한 번 더 요청합니다.

글자가 깨져서 나옵니다

증상. 브라우저에서 열었더니 한글이 알아볼 수 없는 기호로 보입니다.

원인. 메모장에서 저장할 때 인코딩이 UTF-8이 아니었습니다.

해결. 메모장에서 다른 이름으로 저장을 누르고 인코딩을 UTF-8로 바꿔 다시 저장합니다. 파일 형식은 모든 파일, 이름은 index.html입니다.

STEP 03

재료 만들어 붙이기 — 그리고 폴더가 되는 순간

그림과 소리 같은 재료(에셋)를 만들어 앱에 붙입니다. 이 칸을 지나면 앱은 파일 한 개에서 폴더로 바뀝니다. 그 변화가 이 칸의 진짜 내용입니다.

왜 필요한가

한 파일 앱은 뼈대와 재료와 규칙이 한 장에 뭉쳐 있습니다. 짧을 때는 편합니다. 그런데 화면이 늘어나면 어디를 고쳐야 할지 알 수 없게 됩니다. 앱이 되려면 역할이 다른 것들이 각자 자리로 흩어져 폴더에 모여야 합니다.

식당과 같습니다. 인테리어와 조리대와 출입 규정이 한 방에 섞여 있으면 가게를 키울 수 없습니다. 아래는 낚시 게임의 실제 파일 목록입니다.

STEP 04

주소 만들기

여기가 연수의 정점입니다. 지금까지 만든 앱에 인터넷 주소를 답니다. 주소가 생기면 QR 하나로 학생 30명이 같은 앱을 엽니다. 앱의 형태에 따라 길이 둘로 갈리니 어느 쪽인지 먼저 판단합니다.

왜 필요한가

홀도 꾸몄고 재료도 넣었습니다. 그런데 지금 그 앱은 내 노트북에서만 열립니다. 옆자리 선생님 휴대폰으로는 열리지 않습니다. 파일이 그 노트북 안에만 있기 때문입니다.

식당으로 치면 홀과 주방은 다 지었는데 건물에 주소가 없는 상태입니다. 아이들이 들어올 문이 아직 없습니다. 이 칸에서 그 문을 냅니다.

문 내는 방법은 앱의 형태에 따라 갈립니다. 파일이 하나인 앱과 폴더로 이루어진 앱은 올리는 곳이 다릅니다. 그래서 두 길을 나란히 싣습니다.

공개 전에 한 번 멈춥니다. Public 저장소는 전 세계에 공개됩니다. 학생 이름과 얼굴 사진은 올리지 않습니다. 교과서 지문과 삽화가 들어간 앱은 교실 안에서만 씁니다.

이렇게 합니다

판단 기준은 한 문장입니다. 메모장으로 열 수 있는 파일 하나면 A, AI가 폴더를 만들어 줬으면 B입니다.

길 A. 파일 하나를 깃허브 페이지로

메모장으로 열리는 index.html 한 개짜리 앱입니다. 깃허브 무료 호스팅(GitHub Pages)을 켜서 주소를 받습니다. 주소가 내 것이고 오래 남습니다.

  1. github.com에 로그인하고 오른쪽 위 더하기 단추에서 New repository를 고릅니다.
  2. Repository name은 영문 소문자와 숫자 그리고 하이픈만 씁니다. 이 이름이 주소 끝에 그대로 붙으니 짧게 짓습니다.
  3. Public을 고릅니다. Add a README file은 체크하지 않습니다. 그다음 Create repository를 누릅니다.
  4. 다음 화면 가운데의 uploading an existing file 링크를 누릅니다.
  5. 탐색기에서 index.html과 assets 폴더를 함께 선택해 브라우저 화면으로 끌어다 놓습니다. 파일 하나씩이 아니라 폴더째 끌어다 놓습니다.
  6. 목록에 assets가 앞에 붙은 줄이 보이는지 확인하고 아래 Commit changes를 누릅니다.
  7. 저장소 위쪽 Settings 탭을 누르고 왼쪽 사이드바에서 Pages를 누릅니다.
  8. 아래 표대로 세 칸을 맞추고 Save를 누릅니다.
  9. 1분에서 3분 기다립니다. 404가 뜨면 새로고침합니다. Actions 탭에서 초록 체크가 붙으면 완료입니다.
길 A 설정값입니다. Settings 탭의 Pages 메뉴, Build and deployment 칸에 있습니다.

길 B. 폴더 프로젝트를 ai.studio 주소로

AI가 src 폴더와 여러 파일을 만들어 준 앱입니다. 이런 앱은 깃허브에 올려도 그냥 파일 묶음으로만 보입니다. AI Studio Build 화면에서 바로 배포하는 쪽이 빠릅니다.

  1. AI Studio의 Build 화면에서 내 프로젝트를 엽니다.
  2. 오른쪽 위 배포 단추를 누릅니다.
  3. 잠시 뒤 ai.studio로 시작하는 주소가 나옵니다. 그 주소를 복사합니다.
  4. 주소만 보내면 다른 사람이 바로 들어옵니다. 따로 계정을 만들 필요가 없습니다.

이 사다리의 6칸과 7칸과 8칸은 모두 이 길로 갑니다. 세 칸 다 AI Studio Build로 만드는 폴더 프로젝트이기 때문입니다.

배포한 주소도 링크를 받은 사람이면 누구나 엽니다. 공개 범위는 길 A와 같다고 보고 학생 정보를 넣지 않습니다.

두 길이 모두 막히면 플랜 C가 있습니다. Netlify Drop에 내 앱 폴더를 통째로 끌어다 놓으면 몇 초 만에 주소가 나옵니다. 로그인도 필요 없습니다. 다만 계정 없이 올린 사이트는 얼마 뒤 사라지니 오늘 시연용으로만 씁니다.

  • 휴대폰에서 같은 주소를 열어도 똑같이 열립니다.
  • assets 폴더의 그림이 깨지지 않고 그대로 보입니다.

막히면

주소를 열었더니 404가 뜹니다

증상 주소창에 붙여넣었는데 앱 대신 404 화면이 나옵니다.

원인 Save를 누른 직후에는 아직 간판이 켜지지 않았습니다. 켜지는 데 1분에서 3분 걸립니다.

해결 잠시 기다렸다가 새로고침합니다. 저장소 Actions 탭을 열어 pages build and deployment 작업에 초록 체크가 붙었는지 봅니다. 체크가 붙었는데도 404면 주소 끝 슬래시와 저장소 이름 철자를 확인합니다.

앱은 열리는데 그림만 안 보입니다

증상 글자와 버튼은 나오는데 배경 그림이나 캐릭터 자리가 비어 있습니다.

원인 파일을 하나씩 올려 assets 폴더 구조가 깨졌거나 파일명 대소문자가 코드와 다릅니다. 내 노트북은 대소문자를 가리지 않지만 서버는 가립니다.

해결 저장소 목록에 assets 폴더가 보이는지 확인합니다. 없으면 폴더째 다시 올립니다. 파일명은 영문 소문자로 통일하고 코드 안 경로와 한 글자씩 맞춥니다.

Pages 메뉴에 Branch 선택지가 없습니다

증상 Settings에서 Pages를 열었는데 main을 고를 칸이 보이지 않거나 유료 안내가 뜹니다.

원인 저장소를 Private로 만들었습니다. 무료 계정은 Private 저장소에서 깃허브 페이지를 켤 수 없습니다.

해결 Settings 맨 아래 Danger Zone에서 Change visibility를 눌러 Public으로 바꿉니다. 바꾸기 전에 학생 이름과 얼굴 사진, 교과서 지문과 삽화가 파일 안에 없는지 먼저 확인합니다.

결과 모으기

주소가 생겼으니 이제 30명이 같은 앱에 들어옵니다. 그런데 결과는 아직 각자의 기기 안에만 남습니다. 구글 시트와 Apps Script로 결과를 한 곳에 모읍니다. 이 칸에서 처음으로 주방을 짓습니다.

왜 필요한가

지금 앱은 결과를 브라우저 안 저장 공간에 둡니다. 학생이 탭을 닫으면 사라지고 교사는 볼 수 없습니다. 30명의 결과를 한 곳에 모으려면 받아 적는 사람이 필요합니다. 식당으로 치면 주방입니다.

주방을 짓는 가장 쉬운 길이 구글 시트입니다. 시트 하나를 만들고 거기 딸린 프로그램(Apps Script)을 켜면 그것이 곧 서버가 됩니다. 새로 설치할 것도 없고 돈도 들지 않습니다.

그리고 시트가 곧 선생님 대시보드입니다. 교사용 화면은 따로 만들지 않습니다. 필터를 켜고 정렬하고 피벗 테이블을 쓰는 일은 이미 아는 일이라, 앱 안에 관리 화면을 만드는 것보다 빠르고 안전합니다.

이렇게 합니다

  1. 주소창에 sheets.new를 입력해 새 시트를 만들고 이름을 우리반앱서버로 바꿉니다. 아래쪽 탭 두 개를 학급과 기록으로 만들고 1행에 열 이름을 적습니다.
  2. 시트 상단 확장 프로그램 메뉴에서 Apps Script를 누릅니다. 새 탭으로 편집기가 열립니다.
  3. 편집기의 기본 코드를 모두 지우고 서버 코드를 붙여넣은 뒤 저장합니다. 오른쪽 위에 빨간 오류 표시가 없어야 합니다.
  4. 오른쪽 위 배포 단추를 누르고 새 배포를 고릅니다. 유형 선택에서 웹 앱을 고르고 아래 표대로 설정값을 맞춘 뒤 배포를 누릅니다.
  5. 승인 화면이 다섯 단계로 지나갑니다. 액세스 승인을 누르고, 내 개인 Gmail 계정을 고르고, 확인되지 않은 앱이라는 화면에서 왼쪽 아래 고급을 누르고, 맨 아래 우리반앱서버로 이동을 누르고, 권한 목록에서 허용을 누릅니다.
  6. 나온 웹 앱 주소를 복사합니다. 끝이 /exec인지 확인하고 새 탭에 붙여넣습니다. 화면에 ok true 한 줄이 보이면 주방이 문을 연 것입니다.
  7. index.html 맨 위 SERVER_URL 자리에 그 주소를 넣고 학급 코드 입장과 결과 저장을 붙입니다. 붙이는 일은 아래 프롬프트가 합니다.

주문서 양식입니다. 왼쪽이 홀에서 주방으로 보내는 것이고 오른쪽이 주방에서 돌아오는 답입니다.

복붙 프롬프트

index.html 전체를 먼저 붙여넣고 한 줄 띄운 다음 이 프롬프트를 붙입니다. 대괄호로 표시한 두 자리는 내 것으로 바꿉니다.

위에 붙여넣은 index.html은 제가 만든 초등학교 교과 활동 웹앱입니다. 이 앱에 서버 연동을 추가해 주세요.

[역할] 초등학교 교실용 웹앱을 만드는 프론트엔드 개발자입니다. 기존 기능과 디자인은 그대로 두고 기능만 덧붙입니다.

[만들 것] 기존 앱 앞에 학급 코드 입장 화면을 붙이고, 활동이 끝나면 결과를 서버에 보내는 결과 저장 버튼을 추가한 index.html 한 개.

[서버 주소] 코드 맨 위 script 첫 줄에 상수로 둡니다.
const SERVER_URL = "[내 웹 앱 주소, /exec로 끝나는 것]";

[통신 규칙 — 반드시 이대로]
1. method는 항상 "POST"입니다.
2. headers는 { "Content-Type": "text/plain;charset=utf-8" } 입니다. application/json을 쓰지 않습니다.
3. redirect는 "follow"입니다. mode는 no-cors를 쓰지 않습니다.
body는 JSON.stringify(데이터)로 보내고 응답은 await res.json()으로 읽습니다.
이 규칙을 담은 공통 함수 async function callServer(data) 하나만 만들고 모든 통신은 이 함수로 합니다.

[입장 화면]
- 학급 코드 입력칸과 입장 버튼을 둡니다.
- 입장을 누르면 callServer({ action: "join", code: 입력한코드 })를 보냅니다. 앞뒤 공백을 지우고 대문자로 바꿔 보냅니다.
- 응답이 { ok: true, className, size }이면 className을 넣어 인사말을 보여 주고 1부터 size까지 번호 고르기 칸과 별명 입력칸과 시작 버튼을 보여 줍니다.
- 응답이 { ok: false, msg }이면 msg를 입력칸 아래에 보여 줍니다.
- 실명 입력칸은 만들지 않습니다. 번호와 별명만 쓴다는 안내문을 작게 넣습니다.

[결과 저장 버튼]
- 결과가 나오는 자리에 큰 버튼으로 둡니다.
- 누르면 callServer({ action: "save", code, number, nickname, score })를 보냅니다. score는 [내 앱의 결과값 설명]입니다.
- 보내는 동안 버튼을 비활성화하고 글자를 저장 중으로 바꿉니다.
- 성공하면 저장됐어요 알림 문구를 2초간 보여 주고, 실패하면 오류 메시지를 화면에 그대로 보여 줍니다.

[그대로 둘 것] 기존 기능과 문구와 assets 경로와 효과음은 손대지 않습니다. 색과 글꼴도 그대로 씁니다.

[출력] 설명 없이 완성된 index.html 전체를 코드 블록 하나로 주세요.

통신 규칙 세 줄은 빼면 안 됩니다. 구글 Apps Script 웹앱은 이 형태의 요청만 받습니다. 다른 형태로 보내면 브라우저가 막는 오류(CORS)가 나고 저장이 통째로 실패합니다.

이러면 성공입니다

  • /exec로 끝나는 주소를 새 탭에서 열면 ok true 한 줄이 보입니다.
  • 앱에 학급 코드를 넣고 입장을 누르면 우리 반 이름이 인사말에 나옵니다.
  • 결과 저장을 누르면 시트 기록 탭에 지금 시각으로 한 줄이 생깁니다.

막히면

내 노트북에서는 되는데 학생 앱에서 접속이 안 됩니다

증상 학생이 학급 코드를 넣으면 로그인 화면이 뜨거나 아무 응답이 없습니다.

원인 배포할 때 액세스 권한이 있는 사용자가 나만으로 되어 있습니다. 기본값이 나만입니다.

해결 배포 메뉴에서 배포 관리를 열고 연필 모양을 누릅니다. 액세스 권한을 모든 사용자로 바꾸고 버전에서 새 버전을 고른 뒤 다시 배포합니다. 주소는 바뀌지 않습니다.

브라우저 콘솔에 CORS 오류가 뜹니다

증상 저장 버튼을 눌러도 아무 일이 없고 F12 콘솔에 빨간 글씨로 CORS 오류가 남습니다.

원인 통신 규칙 세 줄 중 하나가 지켜지지 않았습니다. Content-Type이 application/json으로 되어 있거나 redirect 줄이 빠졌거나 mode에 no-cors가 들어간 경우입니다.

해결 오류 문장을 그대로 복사해 AI에게 붙여넣고 세 규칙을 다시 적어 줍니다. 항상 POST로 보낼 것, Content-Type은 text/plain;charset=utf-8로 할 것, redirect는 follow로 할 것입니다.

복사한 주소가 /dev로 끝납니다

증상 주소를 새 탭에서 열면 ok true 대신 로그인 화면이나 오류가 나옵니다.

원인 배포된 주소가 아니라 편집기에서만 쓰는 시험용 주소를 복사했습니다.

해결 배포 관리 화면에서 웹 앱 주소를 다시 복사합니다. 끝이 /exec여야 합니다. index.html의 SERVER_URL도 함께 바꿉니다.

서버 체험 — 게임과 기록표

게임을 하나 만들고 점수를 서버에 올립니다. 링크만 보내면 다른 사람이 같은 순위표를 봅니다. 내가 점수를 올리는 순간 상대 화면의 숫자가 새로고침 없이 바뀝니다. 여기까지 해 두면 학급 대항 기록표를 수업 시간에 그대로 띄울 수 있습니다.

왜 필요한가

5칸에서는 학생이 제출한 결과가 구글 시트에 한 줄씩 쌓였습니다. 이번 칸이 다른 점은 두 가지입니다. 실시간과 동시 접속입니다. 시트는 새로고침을 해야 새 줄이 보입니다. 서버에 붙은 앱은 누가 점수를 올리면 내 화면의 순위표가 저절로 바뀝니다. 30명이 같은 순간에 같은 화면을 봅니다.

또 하나 다른 점이 있습니다. 이번에는 콘솔에 들어가 설정을 손으로 만지지 않습니다. AI Studio Build에게 말로 붙여 달라고 합니다. 주방을 직접 짓는 대신 주방을 붙여 달라고 부탁하는 셈입니다. 연결과 인증과 규칙 파일까지 대화만으로 만들어집니다.

이렇게 합니다

  1. AI Studio의 Build에서 게임을 하나 만듭니다. 점수가 남는 게임이 좋습니다. 낚시 게임을 예로 듭니다. 그림과 소리 같은 재료(에셋)는 이미지 생성으로 한꺼번에 뽑아 넣습니다. 3칸에서 한 방식 그대로입니다.
  2. 같은 채팅 칸에 아래 프롬프트를 넣습니다. Build가 Firebase 연결과 익명 로그인을 붙이고 firestore.rules 파일과 실시간으로 화면을 갱신하는 코드까지 만듭니다.
  3. 화면에 Firebase 설정 팝업이 뜹니다. 약관에 동의합니다. 이때 프로젝트가 자동으로 하나 만들어집니다.
  4. 배포하고 링크를 공유합니다. 링크만 받아도 다른 사람이 동시에 들어와 같은 순위표를 봅니다.

STEP 07

서버 활용 — 날짜별 사진 캘린더

월 달력을 띄우고 날짜 칸을 누르면 사진 한 장을 올립니다. 하루에 한 장만 들어가고 모두가 같은 캘린더를 봅니다. 학급 일기나 급식 기록 그리고 학년 행사 사진첩으로 바로 씁니다. 6칸까지 한 것을 모아 쓰는 종합 과제입니다.

왜 필요한가

6칸에서 서버에 올린 것은 점수 한 줄이었습니다. 이번에는 사진 한 장입니다. 글자보다 무겁고 규칙도 더 필요합니다. 하루에 한 장이라는 제한과 사진 크기라는 규격을 먼저 정해야 앱이 무너지지 않습니다.

여기서 중요한 사실이 하나 있습니다. 무료 조건이 설계를 결정합니다. 사진을 통째로 맡아 주는 Firebase Cloud Storage는 2026년 2월 3일부터 결제 계정이 있어야 만들 수 있습니다. 무료로는 쓸 수 없습니다. 그래서 다른 길로 갑니다. 사진을 브라우저 안에서 정사각형 512픽셀 JPEG로 줄이고 품질을 0.7로 낮춘 다음 문자열로 바꿔 Firestore 문서에 저장합니다.

계산이 맞는지 봅니다. 문서 하나에 들어갈 수 있는 크기는 1MB입니다. 512픽셀로 줄인 사진은 60KB에서 110KB 사이입니다. 여유가 충분합니다. 정해진 규격을 지키라는 말이 취향이 아니라 조건이라는 것을 학생에게도 이 숫자로 설명할 수 있습니다.

이렇게 합니다

  1. 만들 것을 먼저 한 줄로 적습니다. 월 달력 화면을 띄우고 날짜 칸을 누르면 사진을 올리며 하루에 한 장만 들어가고 모두가 같은 캘린더를 봅니다.
  2. 6칸에서 만든 Firebase 프로젝트를 그대로 씁니다. 새로 만들지 않습니다. 익명 로그인은 이미 켜 두었으므로 그 스위치를 다시 만질 일이 없습니다.
  3. 아래 프롬프트를 넣습니다. 규격 네 가지를 문장 안에 못박는 것이 이 칸의 요령입니다. 규격을 적지 않으면 AI는 원본 사진을 그대로 올리는 코드를 씁니다.
  4. 배포하고 링크를 공유합니다. 학급에 나눠 줄 때는 얼굴이 나온 사진을 올리지 않는다는 약속을 먼저 합니다.

  • 다른 기기에서 링크를 열어도 같은 사진이 보입니다.
  • 사진이 모두 정사각형으로 보이고 달력 칸 크기가 들쭉날쭉하지 않습니다.

막히면

사진이 안 올라갑니다

증상 파일을 고르면 잠시 멈췄다가 아무 일도 일어나지 않거나 저장에 실패했다는 문구가 뜹니다.

원인 리사이즈를 건너뛰고 원본을 그대로 올려 문서 한도 1MB를 넘겼습니다. 요즘 휴대폰 사진은 한 장에 3MB가 넘습니다.

해결 코드가 원본을 바로 올리고 있지 않은지 확인합니다. 올리기 전에 512픽셀로 줄이는 단계를 넣어 달라고 다시 말합니다.

화질이 너무 나쁩니다

증상 달력에 올린 사진이 뭉개져 보입니다. 글씨가 찍힌 사진은 읽기 어렵습니다.

원인 512픽셀과 품질 0.7이 무료 조건 안에서 쓸 수 있는 상한입니다. 화질이 아니라 한도에 맞춘 값입니다.

해결 더 키우면 문서 한도에 걸려 저장이 통째로 실패합니다. 화질 대신 찍는 방식을 바꿉니다. 가까이에서 밝게 찍고 글씨가 든 장면은 피합니다.

얼굴이 찍힌 사진이 올라갔습니다

증상 학생 얼굴이 나온 사진이 캘린더에 올라와 있습니다. 링크를 아는 사람은 누구나 봅니다.

원인 이 앱은 링크만 있으면 들어올 수 있는 공개 앱입니다. 얼굴 사진은 처음부터 올리면 안 되는 자료입니다.

해결 먼저 그 사진을 지웁니다. 그다음 규칙을 다시 안내하고 필요하면 링크를 새로 만듭니다.

08

STEP 08

앱이 AI를 부르게

지금까지는 내가 AI에게 물어 앱을 만들었습니다. 이번에는 앱이 스스로 AI에게 묻습니다. 학생이 힌트 버튼을 누르면 앱이 대신 물어보고 한 문장을 받아 옵니다. 열쇠를 안전한 곳에 두는 방법이 이 칸의 전부입니다.

왜 필요한가

앱이 스스로 AI에게 물어보려면 열쇠가 필요합니다. AI 사용 열쇠(API 키)입니다. 이 열쇠를 앱 파일 안에 적어 두면 주소를 아는 사람은 누구나 꺼내 갑니다. 인터넷에 올린 파일은 화면에 안 보여도 누구나 내용을 볼 수 있습니다. 남이 쓴 만큼 내 한도가 줄고 요금이 붙기도 합니다.

그래서 열쇠는 홀에 두지 않고 주방이 보관합니다. 5칸에서 만든 Apps Script가 주방입니다. 앱은 질문만 주문서에 적어 주방에 넘깁니다. 주방이 열쇠를 꺼내 Gemini를 부르고 답을 받아 홀로 내보냅니다. 열쇠는 주방 밖으로 나가지 않습니다.

이렇게 합니다

  1. AI Studio 화면 왼쪽 위의 Get API key를 눌러 키를 하나 발급받습니다. 이 화면을 캡처하지 않습니다.
  2. 5칸에서 만든 Apps Script를 엽니다. 왼쪽 톱니바퀴 모양의 프로젝트 설정으로 들어가 스크립트 속성을 찾습니다. 속성 추가를 누르고 속성 이름 칸에 GEMINI_KEY 를 적고 값 칸에 키를 붙여넣은 다음 저장합니다.
  3. 앱이 {action:"ai", question} 형태로 주문서를 보내면 서버가 대신 Gemini를 부릅니다. 앱이 보내는 것은 질문 한 줄뿐입니다.
  4. 힌트 버튼을 홀에 붙입니다. 학생이 누르면 지금 문제를 질문으로 만들어 보내고 돌아온 한 문장을 화면에 띄웁니다.

모델은 두 가지 중에서 고릅니다. 무료로 쓸 수 있는 횟수가 다릅니다.

무료로 쓸 수 있는 횟수

gemini-2.5-flash 10회 250회 답이 길고 꼼꼼합니다. 교사가 자료를 만들 때 씁니다.
gemini-2.5-flash-lite 15회 1,000회 짧은 힌트에 알맞습니다. 우리 반 앱은 이쪽으로 충분합니다.

한 학급 25명이 한 수업에서 세 번씩 눌러도 75회입니다. flash-lite의 하루 1,000회 안에 넉넉히 들어갑니다.

막히면

GEMINI_KEY가 아직 없어요 라는 답이 돌아옵니다

증상 힌트 버튼을 눌렀는데 힌트 대신 키가 없다는 문구가 그대로 화면에 뜹니다.

원인 스크립트 속성의 이름이 코드가 찾는 이름과 다릅니다. 앞뒤 공백이나 소문자 또는 GEMINI-KEY 처럼 하이픈을 쓴 경우가 대부분입니다.

해결 스크립트 속성을 다시 열어 이름이 GEMINI_KEY 인지 한 글자씩 확인합니다. 고친 뒤에는 웹 앱을 다시 배포합니다.

하루 한도를 넘겼다는 답이 옵니다

증상 수업 후반부터 힌트가 돌아오지 않습니다. 한도를 넘겼다는 문구가 보입니다.

원인 무료 횟수는 한 학급이 한 수업에서 쓰는 것을 기준으로 잡혀 있습니다. 여러 학급이 같은 키를 하루에 몰아 쓰면 걸립니다.

해결 모델을 gemini-2.5-flash-lite 로 바꿉니다. 하루 1,000회까지 늘어납니다. 버튼을 연달아 못 누르게 막아 두면 더 안전합니다.

키가 새어 나간 것 같습니다

증상 키를 캡처에 넣었거나 코드에 붙였다가 지웠습니다. 쓴 적 없는 사용량이 올라가 있습니다.

원인 한 번 밖으로 나간 키는 지워도 돌아오지 않습니다. 저장소 기록과 캡처 파일에 그대로 남습니다.

해결 그 키를 즉시 삭제하고 새로 발급받습니다. 키는 공유와 캡처와 코드 삽입이 모두 금지입니다. 있어야 할 곳은 스크립트 속성 하나뿐입니다.

SAFETY

공개하기 전에

여기까지 오면 내 앱에 주소가 생깁니다. 주소가 생긴다는 것은 누구나 열어 볼 수 있다는 뜻입니다. 학생에게 나눠 주기 전에 네 가지를 확인합니다.

확인할 네 가지

어려운 판단은 없습니다. 무엇을 어디에 두느냐의 문제입니다. 열쇠는 서버에 두고 학생 정보는 애초에 받지 않으며 남의 자료는 교실 밖으로 내보내지 않습니다.

API 키

코드에 적지 않고 화면에 띄우지 않으며 캡처해서 공유하지 않습니다. 키는 Apps Script의 스크립트 속성에만 둡니다. 새어 나갔다면 그 키를 삭제하고 새로 만듭니다.

개인정보

학생 이름과 얼굴 사진은 공개 저장소에 올리지 않습니다. 학생은 회원가입 없이 학급 코드와 번호로 들어옵니다. 시트에는 번호와 별명 그리고 점수만 남깁니다.

저작권

교과서 지문이나 삽화가 들어간 앱은 교실 안에서만 씁니다. 인터넷에 공개하지 않습니다. 수업에 쓰는 것과 누구나 볼 수 있게 두는 것은 다른 일입니다.

공개 범위

Public 저장소는 전 세계에 공개됩니다. 주소를 아는 사람이면 누구나 들어옵니다. 학급 코드는 수업이 끝나면 바꿉니다.

공개 전 확인

  • 코드와 캡처 어디에도 API 키가 적혀 있지 않습니다.
  • 학생 이름과 얼굴 사진이 저장소에 올라가 있지 않습니다.
  • 교과서 지문이나 삽화가 든 앱은 주소를 내지 않았습니다.
  • 수업이 끝난 뒤 학급 코드를 바꿀 자리를 알고 있습니다.

Google Apps Script 구글 시트에 딸린 프로그램입니다. 무료입니다. 5칸의 결과 모으기가 여기서 돕니다.

하루 250회는 한 학급 한 수업 분량입니다. 25명이 열 번씩 눌러도 그 안에 들어옵니다. 우리 반 앱은 flash-lite로 충분합니다.
